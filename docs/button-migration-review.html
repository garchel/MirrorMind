Botões: o que muda, como fica e de onde vem

O app tem 97 tags <button> e 286 <Button>. Esta página mostra quais ainda são botão cru, qual regra de CSS já governa o visual de cada um, e como o código fica depois de padronizado — seguindo docs/design-system-maturation.md.

medido em 2026-10-30 branch staging @ 1e9105b fonte: scan dos .tsx e .css previews: CSS real do app

O veredito: quase nenhum pixel muda — e o que muda é correção

O doc antigo dizia que migrar os botões crus quebraria o CSS, porque o elemento deixaria de casar com os seletores de tag. Isso não acontece: <Button> renderiza um <button> com classes a mais. O elemento continua sendo button, e os 83 seletores que já usam :where(button, .ui-button) continuam valendo.

O que muda é o código: de tag crua para <Button variant size>. Mas medir no navegador, com o CSS real, mostrou quatro coisas que a leitura do doc não mostrava: o tamanho xs zera o padding de botão com texto; linhas de texto herdam a fonte de 15px e o size a reduz para 12px; o .ui-button injeta justify-content: center e centraliza linha/menu que era alinhado à esquerda; e o botão cru de modal/vault herda o pill de 46px do base.css, ficando mais alto que o “Cancelar” que já é <Button>. A terceira é a mais perigosa porque não muda altura nem padding — só o lugar do texto. As três últimas são correções, não regressões, mas precisam ser declaradas.

  • 83 seletores de CSS já aceitam .ui-button.
  • 73 botões de produto não têm classe nenhuma.
  • 153 <Button> ainda passam ui-button--* na mão.
  • 2 grupos de glifo ficam idênticos com size="xs".
  • 2 grupos de linha ficam idênticos com size="sm" + 2 linhas de CSS.
  • 2 grupos de ação encurtam de 46px para 34/40px de propósito.
  • 9 contextos de linha/menu precisam de justify-content: normal na onda 0.

Contagem feita lendo cada tag de abertura com controle de chaves e strings (para não confundir => com o fim da tag), e cada regra de CSS com o seletor quebrado por vírgula respeitando parênteses (para não partir :where(button, .ui-button) ao meio).

O que o <Button> injeta

Entender o default é o que evita a regressão. O primitivo (src/components/ui/Button.tsx) sempre emite três coisas:

PropDefaultClasses emitidasEfeito quando não há regra de contexto
variant secondary ui-button--secondary + secondary-button contorno e fundo de botão secundário
size md ui-button--md 40px de altura e padding de 16px
type button — evita submit acidental (já é o caso em quase todos)

A regra de contexto com classes reais (ex.: .workspace-shell .selection-format-popover :where(button, .ui-button)) tem especificidade 0,2,0; a classe de tamanho injetada tem 0,1,0. Então onde existe contexto, o contexto vence a geometria e o pixel não muda. Mas o global do workspace é :where(.workspace-shell) :where(button, .ui-button) — 0,0,0, porque :where() zera a especificidade. Ele perde até para o button do base.css (0,0,1): é por isso que o botão cru de modal herda 46px, e não os 30px que o global parece prometer.

As quatro armadilhas, medidas no navegador.
  1. .ui-button--xs tem uma regra de “glifo solto” que zera o padding quando não encontra .ui-button__icon + elemento. Texto puro não conta como elemento — então size="xs" serve para botão só-ícone, nunca para linha com texto. E a regra tem especificidade 0,3,0 (o :not(:empty) dentro do :has() conta como classe), então ela vence até a regra de contexto de 0,2,0.
  2. Onde o contexto não declara font-size, o botão cru herda 15px do container e o size="sm" injeta 12px. A linha encolhe de 85px para 63px. A correção é uma linha de CSS: font-size: inherit no seletor de contexto. Não use font: inherit: o shorthand também zera o font-weight: 600 do base.css (medido: 600 vira 400).
  3. .ui-button injeta justify-content: center, e as regras de contexto não o resetam. Em linha/menu de largura cheia, o texto sai do canto esquerdo e vai para o centro — sem mudar altura nem padding, então a captura de tela “parece certa” até alguém ler a linha. A correção é justify-content: normal, que é o valor inicial e não altera o botão cru.
  4. O botão cru de modal e de seleção de vault é um pill de 46px do base.css; o <Button> usa a escala (34px em sm, 40px em md). Migrar encurta — e alinha com os botões que já eram <Button> na mesma barra.

Onda 0: o que o CSS precisa antes de migrar

A varredura de contexto achou 16 regras que declaram display: flex/grid e não declaram justify-content. O .ui-button injeta center, então o conteúdo de uma linha de largura cheia sai do canto esquerdo. Quatro são glifo (o centro é o alvo) e três são grupos de ação de largura própria (o centro não muda nada); as nove abaixo são linha/menu e precisam de justify-content: normal. Seis delas também não declaram font-size e precisam de font-size: inherit, senão o size injeta 12px onde o container usa 15px. O font: inherit resolveria o tamanho, mas zeraria o font-weight: 600 do base.css; por isso a onda 0 usa só a propriedade de tamanho.

Por que normal e não start. justify-content: normal é o valor inicial: no grid ele estica a faixa, no flex ele alinha ao início. É no-op para o botão cru e neutraliza o center injetado. start também neutraliza, mas encolhe a faixa do grid para max-content e muda a quebra de linha do texto — ou seja, criaria a regressão que a onda 0 existe para evitar.

A maior dívida: 153 <Button> com classes na mão

O componente existe, mas a maioria ainda fala com ele pela classe: className="ui-button ui-button--secondary ui-button--sm" em vez de variant="secondary" size="sm". O resultado é idêntico (as classes são exatamente as que as props emitem), mas a intenção some: quem lê o código não sabe se aquele botão é secundário porque é uma ação comum ou porque alguém copiou a string.

Por que esta é a onda de menor risco. Trocar className="ui-button ui-button--secondary ui-button--sm" por variant="secondary" size="sm" emite o mesmo conjunto de classes, na mesma ordem de especificidade. Não há decisão de design envolvida — só a passagem da string para as props. É o único grupo em que “não muda pixel” pode ser verificado por comparação de DOM, não por olho.

O plano, em ondas

  1. Onda 0

    Preparar o CSS (sem tocar em TSX)

    Os 9 seletores de contexto que ainda dependem só da tag viram :where(button, .ui-button); os 9 contextos de linha/menu ganham justify-content: normal; os 6 que não declaram fonte ganham font-size: inherit.

    Nenhuma mudança visual: :where tem especificidade zero, normal é o valor inicial e font-size: inherit preserva o font-weight: 600 do base.css (o shorthand font: inherit o zeraria). Commit isolado, sem migrar componente; a verificação é a suíte de render + medição dos 6 contextos.
  2. Onda 1

    Os 73 botões crus de produto

    Vira <Button variant size> com a variante declarada em cada grupo da tabela.

    Validação: tsc -b, suíte completa, e um E2E por contexto (popover de formatação, barra flutuante, busca de notas, menu do explorador, ações de modal, seleção de vault).
  3. Onda 2

    Os 14 botões com classe dinâmica

    Mesma troca, preservando className (is-selected, indexadora-menu-item, is-danger).

    Estes dependem de estado; a classe continua sendo o canal do estado, não da aparência.
  4. Onda 3

    As 153 classes manuais em <Button>

    className="ui-button ui-button--secondary ui-button--sm" vira variant="secondary" size="sm".

    Zero risco visual por construção. Pode ser feito por arquivo, com o teste do arquivo como rede.
  5. Fora

    RootErrorBoundary

    Um botão com estilo inline, fora do workspace. Migrar exige decidir se o boundary de erro usa o design system ou continua autônomo.

    Não entra nesta frente: o boundary precisa funcionar mesmo se o CSS do app falhar.

Como os números foram obtidos

Três scripts locais, sem dependência nova. O primeiro lê cada .tsx e encontra a tag de abertura com controle de chaves, strings e templates (para não terminar a tag no > de uma arrow function). O segundo lê cada .css, remove comentários preservando linhas, e quebra a lista de seletores por vírgula em profundidade zero de parênteses. O terceiro acha as regras de contexto que declaram display sem justify-content.
